# flashos — the flash driver and algorithm n32h7x_cmsisdap.tcl uses

Three files, copied here from the ns-link tree's `flashop/` so this config needs no
second checkout. `n32h7x_cmsisdap.tcl` sources the first by this directory's name, so
moving or renaming any of them breaks the flash.

| file | what it is |
|---|---|
| `flashos.tcl` | the driver: SRAM layout, the BKPT call protocol, EraseRange, the double-buffered program loop with its timing report |
| `flashop.bin` | the algorithm, 612 bytes, loaded into SRAM and called there. Built from `FlashPrg.c` by `flashop/Makefile` in the ns-link tree. |
| `flashop_sym.tcl` | the six entry offsets and the blob length, generated from the linked ELF. `flashos.tcl` refuses to load without it. |

Provenance: copied 2026-09-21 from `ns-link/flashop/`. `flashop.bin` md5
`9e5d3771636f17cdedb57a6f66ce8741`, sha256[:16] `47fbf53de68a7e0f` — the hash
`flashop_sym.tcl` records, so the two agree with each other and with the ELF they
were generated from. To refresh, `make -C flashop` in that tree and re-copy all
three; `flashop_sym.tcl` is regenerated by the build and must not be hand-edited.

This is not the same algorithm as `../flash_op/n32h7xx_flash_op.bin`, the vendor blob
this config used to drive. That one has six fixed entry points and its geometry
compiled in; this one has eight, takes its geometry from a parameter block in SRAM,
and adds `EraseRange` (which is what replaces 135 round trips with one) and
`FlashSum`. `flash_op/` is left in place and is no longer used by anything here.

## What changed in the config

`n32h7x_flash` kept everything it did to prepare the target — `n32h7x_connect` and
the AP0 boot window, the halted-CPU validation, `n32h7x_quiesce_cached_m7`, the M4
and camera reset, the SysTick/exception/interrupt/MPU preparation — and then hands
the run to `flash_program_bin`, which stages the blob, verifies it in SRAM, erases
the range, programs and verifies each chunk, and calls UnInit. The vendor call
protocol the old loop used (`n32h7x_flashos_call`, `n32h7x_wait_flashos_halt`, the
profile procs) is still in the file and is now unused.

## Where the algorithm and its buffers live

CM7 upper DTCM at **0x20050000**, inside the `DTCM (rw) : ORIGIN = 0x20020000,
LENGTH = 0x60000` region declared by `LinkFile/n32h787_kws_demo_CM7.ld` — the
layout needs 128 KiB (0x20000) of the 192 KiB window starting there. The config
carries the full reasoning; the short version is that this is the third base the
layout has had and the first two failed silently:

* `0x24000000` — CM7 AXI SRAM. Overlaps the CM4's camera DMA buffer and the CM7's
  own `.data`/`.bss`; staging over the latter corrupted ~250 bytes of a chunk.
* `0x30010000` — AHB SRAM1, which is what this config used when it drove the vendor
  blob. A 16 KiB buffer fits there; the 62 KiB pair does not. Only 24 KiB exists
  before `SNAPSHOT` at 0x30016000, and per the CM7 linker script what follows that
  is the CM4's own `RW_SRAM`.

Neither failure was visible from inside the pipeline, because `Verify` compares the
buffer against the flash that buffer just programmed, and a readback would have
compared the flash against the same buffer. Both agree, because both hold the same
wrong bytes. DTCM cannot fail that way: no DMA engine and no other core has an
address for it, and it is not cacheable, so the D-cache maintenance the other two
layouts needed is a no-op.

The CM7 application does use DTCM — the `.kws_arena` / `.kws_model` sections — but
the model is copied back out of Flash and the arena rebuilt on every boot, and this
flow ends in `reset run`.

## Measured

Full 551172-byte combined image, probe `360111503035573537145928` on the H787,
2026-09-21. `make -C firmware/Makefile flash`, wall clock:

| | before | after |
|---|---|---|
| erase | ~2.4 s (135 `EraseSector` calls) | **10 ms** (one `EraseRange`, hidden behind chunk-0 staging) |
| stage | ~4.3 s (34 × 16 KiB chunks) | 2984 ms (9 × 62 KiB chunks, 180 KiB/s) |
| program | ~2.3 s | **222 ms** (hidden behind the next chunk's staging) |
| verify | ~0.7 s | 197 ms |
| **total** | **13 s** | **5.7 s** |

`erase` and `program` are not the erase and the flash write any more — they are the
parts of each that the staging did not cover, which is why they have no rate column.
They should sit near zero; if either grows, an overlap has stopped happening.

Adapter clock sweep, same image, flash phase only:

| requested | stage | total |
|---|---|---|
| 2000 kHz | 4645 ms | 5.27 s |
| 3000 kHz | 4183 ms | 4.78 s |
| 5000 kHz | 4181 ms | 4.76 s |
| **6000 kHz** | **2997 ms** | **3.51 s** |
| 8000 kHz | 3000 ms | 3.53 s |

The knee is 6000, and it is the probe rather than the target: past it the bit loop
stops being paced and free-runs, so a higher request changes nothing. `ADAPTER_KHZ`
in the Makefile defaults to 6000 for that reason. The Makefile's old note that
"4 MHz wedges the NSLink HID endpoint" was about a backend this config no longer
uses — openocd logs `Using CMSIS-DAPv2 interface`, i.e. `usb_bulk` — and 6000 and
8000 are both measured clean.

## What has and has not been run

**Run**, on the H787, 2026-09-21: the full `make -C firmware/Makefile flash` at
6000 kHz, and the seven-point clock sweep above. After it, the flash was dumped over
SWD and compared against the image — **551172 bytes, byte-identical**. That compare
is the one that matters, because the on-target `Verify` per chunk compares the flash
against the buffer it was programmed from and cannot see a staging error; only the
host holds the original.

**Boot check**, immediately after: `VTOR = 0x15006000` (the application's own
`SystemInit`, i.e. the image's startup code ran), `CFSR = 0`, and the PC in ITCM.
Byte-identical content does not imply a board that runs, which is why this was read
separately.

**Also run**: the application-only flash at a custom start address (the DEMO's
`make flash`, equivalent to the former `flash-app`, programming 250836 bytes at
0x15006000) was verified on the H787 on 2026-09-23, including the automatic TCM
partition provisioning on a chip whose DTCM was disabled at default partition.
The driver's own host-side checks in the ns-link tree (39 offline tests covering
arithmetic and parsing) are unchanged by this port.
